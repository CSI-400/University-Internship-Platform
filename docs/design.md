# UI/UX Design — University Internship Platform

**สถานะ:** แนวทางออกแบบหน้าจอสำหรับทีม พัฒนาต่อจาก [README หลัก](../README.md) หัวข้อ 8; ยังไม่ใช่ภาพ mockup หรือหน้าจอที่ implement แล้ว<br>
**อ่านร่วมกับ:** [API Contract](api-contract.md), [System Architecture](architecture.md), [Design Diagrams](diagrams.md) และ [Verification Rules & Risk Score](<../Verification Rules & Risk Sco.txt>)

เอกสารนี้แปลงแนวทาง UI/UX ของ PM เป็นรายการหน้าจอ องค์ประกอบ และสถานะที่ทีมออกแบบ/พัฒนาได้ กฎสิทธิ์และผลลัพธ์จริงให้ยึด API Contract และกฎธุรกิจของ PM หากข้อความในเอกสารนี้ต่างจากกฎต้นทาง ให้แก้เอกสารนี้ให้ตรงก่อนพัฒนา

## 1. เป้าหมายของหน้าจอ

- นักศึกษาเห็นประเภทงาน เบี้ยเลี้ยง รีวิว และระดับความน่าเชื่อถือก่อนตัดสินใจสมัคร
- HR รู้ว่าบริษัทต้องยืนยันตัวตนหรือรอผลตรวจอะไร และเห็นความคืบหน้าไปสู่ Tier 2
- Admin แยกคิวตรวจงาน คิว Report และคิว KYB ได้ชัด โดยเห็นเหตุผลที่ระบบให้คะแนนหรือพักงาน
- Supervisor เห็นหลักฐานและเงื่อนไขก่อนยืนยัน On-Site หรืออนุมัติ E-Certificate

การใช้สีเป็นตัวช่วยอ่านสถานะ ต้องมีข้อความหรือไอคอนกำกับเสมอ ผู้ใช้จึงเข้าใจสถานะได้แม้แยกสีไม่ออก

## 4. องค์ประกอบสำคัญ

ข้อมูลที่หน้าจอใช้แยกตามบริการเจ้าของข้อมูล; Web เรียกผ่าน Gateway และไม่เดาสถานะ Tier หรือผลตรวจจากสีที่แสดง:

| องค์ประกอบ | แหล่งข้อมูลใน API Contract |
| --- | --- |
| รายการ/รายละเอียดงานและ Featured | `GET /v1/jobs`, `GET /v1/jobs/{job_id}` จาก Job Management |
| ชื่อบริษัท, Tier และ On-Site Badge | `GET /v1/companies/{company_id}/public-profile` จาก Identity |
| ดาวเฉลี่ยและจำนวนรีวิว | `GET /v1/companies/{company_id}/review-summary` จาก Student Experience; หากยังไม่มีรีวิวให้แสดง “ยังไม่มีรีวิว” |
| ความคืบหน้า Tier 2 ของ HR | `GET /v1/companies/me` ฟิลด์ `tier_progress` จาก Identity |
| ตารางผลตรวจเขียว/เหลือง/แดง | `GET /v1/admin/job-verifications` จาก Verification; รายการที่ Admin ตัดสินได้อ่านจาก `GET /v1/admin/job-reviews` |
| คำขอออก Certificate ของ Supervisor | `GET /v1/supervisor/certificate-requests` จาก Student Experience |

### Structured Job Card และหน้ารายละเอียด

การ์ดงานตาม README แสดงชื่อประกาศ, บริษัท, หมวดงาน (`TECH_IT`, `BUSINESS_MARKETING`, `CORPORATE_SERVICES`), เบี้ยเลี้ยงหรือข้อความว่าไม่ระบุ, คะแนนดาวจากรีวิว และป้ายสถานะบริษัท เมื่อเป็น Featured ให้แสดงป้ายแยกจากป้าย Verified เพราะ Featured เป็นการจัดแสดง ไม่ใช่ผลตรวจความปลอดภัย หน้าค้นหาแสดงเฉพาะงาน `PUBLISHED`; งาน Featured ที่เผยแพร่แล้วเรียงก่อนงานทั่วไปตาม [API Contract](api-contract.md)

หน้ารายละเอียดเพิ่มคำอธิบายงาน สวัสดิการ และปุ่มสมัคร/Report สำหรับนักศึกษาที่มีสิทธิ์ ถ้างานเปลี่ยนเป็น `VERIFYING`, `SUSPENDED` หรือสถานะอื่นที่ไม่เผยแพร่ ต้องไม่เปิดรายละเอียดสาธารณะหรือแสดงเนื้อหาเก่าระหว่างรอตรวจ

### Trust Progress Bar สำหรับ HR

แสดงเงื่อนไข Tier 2 เป็นข้อความพร้อมตัวนับ **งานใหม่คนละ `job_id` ที่เผยแพร่สำเร็จ 0–3 งาน** และ **ผลประเมิน Pass อย่างน้อย 1 รายการ** งานที่ Auto-Approve และ Admin Approve นับเหมือนกัน การแก้/เผยแพร่ซ้ำงานเดิมไม่เพิ่มตัวนับ Report ที่ยังรอ Admin ตรวจไม่ตัดสิทธิ์; หาก `has_confirmed_report = true` ให้แจ้งว่าบริษัทไม่เข้าเงื่อนไข Tier 2 โดยไม่เปิดเผยรายละเอียดผู้รายงาน

ป้าย On-Site Verified แสดงได้เฉพาะเมื่อบริษัทเป็น Tier 2 และวันปัจจุบันยังไม่ถึงวันหมดอายุ 1 ปีตามกฎ PM; เมื่อหมดอายุต้องหายจากมุมมองสาธารณะ

### Traffic-Light Admin Queue

หน้า **ผลตรวจประกาศ** แสดงสีเขียวเมื่อผลเป็น `PUBLISHED`, สีเหลืองเมื่อ `PENDING_REVIEW`, สีแดงเมื่อ `AUTO_REJECTED` (คะแนน `≥ 70` หรือพบ Blacklist ใน `job_title`/`description`) รายการต้องมีคะแนน เหตุผล คำที่พบ และเวลา/เวอร์ชันที่ตรวจ เพื่อแยกประวัติผลตรวจจากสถานะปัจจุบัน คิวที่ Admin กด Approve/Reject ได้มีเฉพาะเคส `PENDING_REVIEW` ที่ยังเปิดอยู่

คิว **Report** เป็นคนละส่วนกับคิว Risk Score: Tier 1 ถูกซ่อนเป็น `SUSPENDED` เมื่อถูกรายงานจากนักศึกษา 3 บัญชีไม่ซ้ำกัน; Tier 2/On-Site เข้าคิวสีเหลืองตั้งแต่ Report แรกโดยยังไม่ลด Tier และประกาศยัง `PUBLISHED` จนกว่า Admin จะตัดสิน ต้องแสดงจำนวนผู้รายงานที่ไม่ซ้ำกันและผล `CONFIRM`/`DISMISS` ชัดเจน

## 5. สถานะและข้อความที่ UI ต้องสื่อ

| เหตุการณ์ | สิ่งที่ผู้ใช้ควรเห็น |
| --- | --- |
| บริษัท Tier 0 กดส่งงาน | แจ้งว่าต้องผ่าน e-KYB และ Admin อนุมัติก่อน; ยังบันทึก Draft ได้ |
| HR ส่งงานหรือแก้งานที่เคยเผยแพร่ | แสดง `VERIFYING` และซ่อนประกาศจากหน้าสาธารณะทันที ไม่แสดงเนื้อหาเก่า |
| ผลตรวจคะแนนปานกลาง | แสดง `PENDING_REVIEW` และข้อความว่ารอ Admin ตัดสิน ไม่บอกว่าเผยแพร่แล้ว |
| พบคำต้องห้ามหรือคะแนนสูง | แสดง `AUTO_REJECTED` พร้อมเหตุผลที่ API อนุญาตให้เปิดเผย |
| API ตอบ `202` | แสดงว่า “รับคำขอแล้ว กำลังดำเนินการ” และติดตามสถานะต่อ ไม่แสดงผลสำเร็จขั้นสุดท้ายทันที |
| นักศึกษาฝึกจบและได้รับ Fail | ยังเปิดให้เขียนรีวิว และติดป้ายกำกับผล Fail บนรีวิว |
| ขอ Certificate ก่อนครบ 30 วันหรือยังไม่ผ่านเงื่อนไข | แสดงเหตุผลที่ยังอนุมัติไม่ได้; UI ปิดปุ่มได้แต่ server ต้องตรวจซ้ำ |

ทุกหน้าที่ดึงข้อมูลควรมีสถานะกำลังโหลด, ไม่มีข้อมูล, โหลดไม่สำเร็จ และข้อความเมื่อไม่มีสิทธิ์เข้าถึง โดยไม่แสดงรายละเอียดเอกสาร KYB หรือ Resume ให้ผู้ที่ไม่มีสิทธิ์

## 6. ขอบเขตการออกแบบและลำดับทำหน้าจอ

| ช่วงงานตาม README | หน้าจอที่ควรทำให้ครบ flow ก่อน |
| --- | --- |
| Week 1 | สมัคร/เข้าสู่ระบบของบทบาทที่ใช้เดโม, HR ส่ง KYB และ Admin ตรวจ KYB |
| Week 2 | HR สร้าง Draft/ส่งตรวจ, หน้าสถานะงาน และ Admin Queue สำหรับผลเขียว/เหลือง/แดง |
| Week 3 | หน้าแรก (Index), ค้นหา/รายละเอียด/สมัครงานของนักศึกษา และหน้า Report กับ Admin Report Queue |
| Week 4 | ผลประเมิน Pass/Fail, รีวิว, Supervisor On-Site/Certificate และ UAT 9 เคส |

Featured ในเดโม v1 คือป้ายและลำดับงานจากข้อมูลที่ทีมเตรียมไว้ ไม่มีหน้าจอซื้อหรือชำระเงิน Express KYB/Fast-Track Review ยังไม่มีเกณฑ์ราคา/สิทธิ์ในแผนหรือ UAT จึงไม่เพิ่มหน้าคิวแบบชำระเงิน ส่วน HR Pro Subscription เป็น Future Phase ตาม README

กราฟบน Dashboard ให้ใช้เฉพาะเมื่อช่วยให้ผู้ใช้ตัดสินใจจริง หากใช้ ApexCharts ใน Next.js ต้องโหลด `react-apexcharts` ด้วย dynamic import ใน Client Component และ `ssr: false` ตาม [Project Setup Handoff](project-setup.md) เพื่อเลี่ยง `window is not defined`

## 7. Prompt สำหรับสร้างหน้าจอด้วย Gen AI ทีละหน้า

ใช้ **หนึ่ง prompt ต่อหนึ่งหน้าจอ** ด้านล่างเพื่อสร้าง mockup ก่อนนำไปพัฒนา Prompt แต่ละข้อระบุผู้ใช้ งานหลัก เนื้อหา สถานะ และโทนภาพในตัวเอง จึงคัดลอกแยกไปใช้ได้ ให้สร้างตัวอย่างทั้งเดสก์ท็อปและมือถือโดยจัดลำดับข้อมูลใหม่ตามพื้นที่ ไม่ย่อทั้งหน้าจอให้เล็กลงอย่างเดียว ข้อความ/ตัวเลขในภาพเป็นข้อมูลตัวอย่าง; ตรวจคำภาษาไทย สิทธิ์ สถานะ และกฎจริงกับ [API Contract](api-contract.md) ก่อนส่ง PM หรือเขียนโค้ด อย่าให้ Gen AI เพิ่มการชำระเงิน การรับประกันความปลอดภัย หรือผลอนุมัติที่ระบบยังไม่ได้ยืนยัน

### ผู้เข้าชมและนักศึกษา

#### 7.1 หน้าแรก (Index)

> ออกแบบหน้าแรก (Index) สาธารณะของ University Internship Platform เป็นเว็บ responsive ภาษาไทย โทนสว่าง พื้นขาว `#FFFFFF`/เทาอ่อน `#F8FAFC` ปุ่มหลักน้ำเงิน `#2563EB` มีแถบนำทางพร้อมโลโก้ ค้นหางาน เข้าสู่ระบบ และสมัครบัญชี ส่วน hero อธิบายว่าแพลตฟอร์มช่วยค้นหางานฝึกงานและดูข้อมูลบริษัทก่อนสมัคร พร้อมช่องค้นหาและปุ่มไปหน้าค้นหางาน ตามด้วยทางลัด 3 หมวด Tech & IT, Business & Marketing, Corporate Services และตัวอย่าง Structured Job Card ของงาน `PUBLISHED` ที่แสดงชื่องาน บริษัท หมวด เบี้ยเลี้ยงหรือ “ไม่ระบุ” คะแนนรีวิวหรือ “ยังไม่มีรีวิว” ป้ายบริษัทที่มีสิทธิ์แสดง และ Featured แยกจากป้ายความน่าเชื่อถือ มีส่วนอธิบายความหมายของการตรวจสอบและ Tier แบบไม่รับประกันความปลอดภัย มีทางไปสมัครนักศึกษาและสมัครบริษัท แสดงสถานะกำลังโหลด ไม่มีงาน และโหลดงานล้มเหลวโดยไม่สร้างสถิติหรือคำรับรองที่ไม่มีข้อมูลจริง จัด hero และการ์ดใหม่ให้อ่านง่ายบนมือถือ

#### 7.2 สมัครบัญชีนักศึกษา

#### 7.3 สมัครบัญชีบริษัท

> ออกแบบหน้าผลตรวจประกาศสำหรับ Platform Admin เป็นเว็บ responsive โทนสว่าง พื้นขาว/เทาอ่อน น้ำเงิน `#2563EB` ภาษาไทย แยกแท็บประวัติผลตรวจและคิวตัดสิน ประวัติมีป้ายเขียว `PUBLISHED`, เหลือง `PENDING_REVIEW`, แดง `AUTO_REJECTED` พร้อมคะแนน เหตุผล คำต้องห้ามที่พบ เวอร์ชันงาน และเวลาตรวจ; ปุ่ม APPROVE/REJECT อยู่เฉพาะเคส `PENDING_REVIEW` ที่ยัง OPEN มีช่องเหตุผลเมื่อปฏิเสธ หลังตัดสินที่ API รับ `202` แสดงกำลังนำผลไปใช้ ไม่ขึ้นว่าเผยแพร่สำเร็จจนสถานะงานยืนยัน

#### 7.20 คิว Report และการตัดสิน

> ออกแบบหน้าคิว Report สำหรับ Platform Admin เป็นเว็บ responsive โทนสว่าง พื้นขาว/เทาอ่อน น้ำเงิน `#2563EB` ภาษาไทย แยกจากคิว Risk Score แสดงงาน บริษัท Tier จำนวนผู้รายงานไม่ซ้ำกัน เหตุผลและหลักฐานที่มีสิทธิ์ดู Tier 1 เข้าคิวหลัง 3 บัญชีและงานถูก `SUSPENDED`; Tier 2/On-Site เข้าคิวตั้งแต่ Report แรกโดยงานยัง `PUBLISHED` จนมีคำตัดสิน มีปุ่ม CONFIRM/DISMISS ช่องเหตุผล และตัวเลือก suspend job เมื่อ CONFIRM หลังส่งผล `202` แสดงว่ากำลังดำเนินการโดยไม่เดาว่าลด Tier หรือระงับงานเสร็จแล้ว

#### 7.21 จัดการคำต้องห้าม

> ออกแบบหน้าจัดการ Blacklist Keywords สำหรับ Platform Admin เป็นเว็บ responsive โทนสว่าง พื้นขาว/เทาอ่อน ปุ่มหลักน้ำเงิน `#2563EB` ภาษาไทย มีตารางคำต้องห้ามและหมวดคำ ช่องเพิ่ม keyword กับ category ปุ่มลบพร้อมกล่องยืนยันและการแจ้งผล แสดง empty/loading/error state และจำกัดการแก้ไขไว้เฉพาะ Admin ให้เห็นผลต่อการตรวจประกาศเป็นคำอธิบายสั้น ๆ ไม่แสดงว่าการเพิ่มคำทำให้ประกาศเดิมถูกตัดสินย้อนหลังทันที

### Supervisor

#### 7.22 ยืนยันการลงพื้นที่ On-Site

> ออกแบบหน้าบันทึก On-Site Verification สำหรับ Supervisor เป็นเว็บ responsive โทนสว่าง พื้นขาว/เทาอ่อน ปุ่มหลักน้ำเงิน `#2563EB` ภาษาไทย มีข้อมูลบริษัท วันที่ลงพื้นที่ ผล `PASS`/`FAIL` และช่องบันทึกหมายเหตุ พร้อมกล่องยืนยันก่อนส่งและสถานะผลบันทึก อธิบายว่า On-Site Verified Badge จะแสดงสาธารณะเฉพาะบริษัท Tier 2 ที่ผลยังไม่หมดอายุ 1 ปี ไม่แสดง Badge ทันทีเพียงเพราะเปิดฟอร์มหรือเลือก PASS

#### 7.23 คำขอและการอนุมัติ E-Certificate

> ออกแบบหน้าคิว Certificate สำหรับ Supervisor เป็นเว็บ responsive โทนสว่าง พื้นขาว/เทาอ่อน น้ำเงิน `#2563EB` ภาษาไทย มีรายการผู้ฝึกที่ COMPLETED และ PASS พร้อมบริษัท วันเริ่ม/สิ้นสุด ระยะฝึก สถานะ `eligible` และเหตุผลหากยังไม่ครบ 30 วัน ให้เปิดรายละเอียดแล้วเลือก APPROVE/REJECT โดย REJECT ต้องมีเหตุผล ปิดปุ่ม APPROVE สำหรับผู้ที่ยังไม่เข้าเงื่อนไขและแสดงข้อความอธิบาย ผลอนุมัติสำเร็จจึงแสดงใบรับรองให้เจ้าของดาวน์โหลด มีสถานะคิวว่าง กำลังโหลด และผิดพลาด

## 8. ก่อนส่งงาน UI

- ตรวจหน้าจอขนาดมือถือและเดสก์ท็อป รวมถึงการอ่านป้ายสถานะโดยไม่พึ่งสีเพียงอย่างเดียว
- ตรวจข้อความและปุ่มกับสิทธิ์ทั้ง `STUDENT`, `COMPANY_HR`, `PLATFORM_ADMIN`, `SUPERVISOR`
- ทดสอบว่าหน้าสาธารณะไม่เห็นงานที่ถูกซ่อน และผลตอบ `202` ไม่ถูกแสดงเป็นผลสำเร็จขั้นสุดท้าย
- เมื่อชื่อฟิลด์ สถานะ หรือ flow เปลี่ยน ให้แก้หน้าที่เกี่ยวข้องพร้อม [API Contract](api-contract.md) และ [Design Diagrams](diagrams.md)
